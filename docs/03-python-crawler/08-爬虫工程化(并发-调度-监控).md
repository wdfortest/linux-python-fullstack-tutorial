## 8.2 事件循环 30 秒版与 async/await 速成

**心智模型**：事件循环（event loop）是一个单线程调度器，手里有一摞协程（coroutine）。协程执行到 `await` 时**主动让出**：「我要等网络 IO，先让别人用线程」；IO 完成后事件循环把协程唤醒继续跑。一个线程在 IO 等待的空档里轮转多个协程——**并发来自「不闲着等」，不是「多开线程」**。

```python
import asyncio

async def fetch(n: int) -> str:        # async def 定义协程函数
    await asyncio.sleep(1)              # await 处让出控制权(这里用 sleep 模拟 IO)
    return f"page-{n}"

async def main() -> None:
    # gather 并发运行全部协程,按提交顺序收集结果
    results = await asyncio.gather(fetch(1), fetch(2), fetch(3))
    print(results)                      # 三个各 1s 的任务,总耗时约 1s 而非 3s

asyncio.run(main())                     # 事件循环的入口
```

最小必要语法就这几样：`async def` 声明协程；`await` 等待并让出；`asyncio.gather(*tasks)` 并发收集；`asyncio.run()` 启动。**哪些代码能「并发」取决于 await 的点在哪**：协程里的 CPU 密集计算（正则、json 解析）不会让出控制权，会阻塞整个循环——所以采集器里尽量让协程只做「发请求、等响应」这些 IO。

## 8.3 asyncio + httpx：并发与礼貌的合并公式

httpx 是「requests 的现代版」：API 相似、原生支持 async。`AsyncClient` 相当于第 2 章 Session 的异步版（连接池复用）。并发采集的完整纪律是两条，**缺一不可**：

- **`Semaphore` 限并发**：同时在飞的请求最多 N 个——少占你的时间（带宽、内存、被限流风险）；
- **每请求后 sleep 限速**：保证对同一站点的**请求间隔** ≥ 0.3s——少占服务器的时间（呼应第 6 章：并发高不等于间隔短，但如果只限并发不限速，服务器看到的仍是连续轰炸）。

这就是 lab `08_async_httpx.py` 的核心结构（完整文件见 `projects/crawler-lab/08_async_httpx.py`）：

```python
import asyncio
import httpx

MAX_CONCURRENCY = 5     # 信号量:同时进行的请求数上限
DELAY_SECONDS = 0.3     # 每个请求之后的礼貌间隔

async def fetch_page(client: httpx.AsyncClient, sem: asyncio.Semaphore,
                     page: int) -> str:
    """抓一页:先抢信号量,再请求,再限速。三步都不能省。"""
    async with sem:                                   # 最多 5 个协程同时进入
        resp = await client.get(f"{BASE_URL}/page/{page}/", headers=HEADERS)
        resp.raise_for_status()
        await asyncio.sleep(DELAY_SECONDS)            # 限速发生在每个请求之后
        return resp.text

async def main() -> None:
    start = time.time()
    sem = asyncio.Semaphore(MAX_CONCURRENCY)
    async with httpx.AsyncClient(timeout=10) as client:
        # 一次性提交 10 个协程,由事件循环 + 信号量共同调度
        tasks = [fetch_page(client, sem, p) for p in range(1, 11)]
        results = await asyncio.gather(*tasks, return_exceptions=True)
    ...
```

### 8.3.1 异常处理：gather 的 return_exceptions

`asyncio.gather(*tasks, return_exceptions=True)` 让异常**作为结果返回**而不是炸掉整批——某一页失败不影响其他页，事后统一结算：

```python
for page, result in enumerate(results, start=1):
    if isinstance(result, Exception):
        errors.append((page, result))     # 失败页进入重试队列(8.5 节)
    else:
        all_quotes.extend(parse_page(result))
```

默认（`return_exceptions=False`）时第一个异常会直接抛出并**取消其余任务**——批量采集必须显式开 True。

## 8.4 方案对比：asyncio vs ThreadPoolExecutor

不用 asyncio 也能并发——线程池把每个请求丢进一个线程：

```python
from concurrent.futures import ThreadPoolExecutor
import requests

def fetch(page: int) -> str:
    resp = requests.get(f"{BASE_URL}/page/{page}/", headers=HEADERS, timeout=10)
    resp.raise_for_status()
    time.sleep(DELAY_SECONDS)          # 限速同样要有
    return resp.text

with ThreadPoolExecutor(max_workers=5) as pool:   # max_workers = 并发上限
    results = list(pool.map(fetch, range(1, 11)))
```

| 维度 | asyncio + httpx | ThreadPoolExecutor |
|---|---|---|
| 并发模型 | 单线程 + 事件循环，协程极轻 | 每任务一个 OS 线程（默认上限约几 MB/线程） |
| 适合规模 | 成百上千并发 IO | 几十到一两百并发 |
| 代码生态 | 需要 async 生态（httpx/aiohttp） | 同步库直接用（requests/scrapy 的 pipeline 函数） |
| 混用 CPU 密集代码 | 阻塞整个循环（大忌） | 天然无此问题 |
| 学习成本 | 心智模型新 | 心智模型旧（但有线程安全问题） |
| 本仓库选择 | **主推**（采集场景几乎全是 IO 等待） | 快速给存量同步代码加并发 |

选型建议：**新写的采集器用 asyncio**；给已有同步代码快速加并发、或混用大量同步库时，线程池是务实的过渡方案。两边都要记住：并发数要设上限，限速一个都不能少。

## 8.5 断点续爬与重试队列

### 8.5.1 断点续爬：已抓 URL 集合持久化

脚本被 Ctrl+C、被 OOM、被断网杀死后，重跑不应该从头再抓一遍（浪费请求，也违背礼貌）。核心是**把「进度」持久化**：一个 JSON 文件记录已抓 URL 集合，启动时加载，抓完一个记一个：

```python
import json
from pathlib import Path

STATE_PATH = Path("data/crawl_state.json")

def load_state() -> set[str]:
    if STATE_PATH.exists():
        return set(json.loads(STATE_PATH.read_text(encoding="utf-8")))
    return set()

def save_state(seen: set[str]) -> None:
    STATE_PATH.write_text(json.dumps(sorted(seen), ensure_ascii=False), encoding="utf-8")
```

使用模式（伪代码骨架）：

```python
seen = load_state()
for url in todo_urls:
    if url in seen:                 # 已抓过 -> 跳过,不发请求
        continue
    html = fetch(url)
    process(html)
    seen.add(url)                   # 抓完一个记一个(不是全部抓完才记)
    save_state(seen)                # 小规模直接整文件重写;大规模换 SQLite(第 4 章技能)
```

要点：**每个 URL 抓完立刻落盘进度**，崩溃最多丢当前一个；生产规模（百万级 URL）把 JSON 换成 SQLite 表 + 唯一索引（第 4 章 4.6 的三层去重在此合流）；Scrapy 用户的对应物是 `JOBDIR` 持久化（框架替你做了）。

### 8.5.2 重试队列

失败 URL 不能丢也不能立刻硬重试。最小可行实现：

```python
retry_queue: list[tuple[str, int]] = []   # (url, 已重试次数)

def handle_failure(url: str, attempt: int) -> None:
    if attempt < MAX_RETRIES:
        retry_queue.append((url, attempt + 1))
        wait = 2 ** attempt                 # 指数退避:1s, 2s, 4s...
        time.sleep(wait)
    else:
        logger.error("超过最大重试,放弃: %s", url)   # 放弃也要留痕,别静默
```

重试的三条纪律（第 2 章 2.4.2 的展开）：指数退避；**429 不进重试队列**（进降速逻辑）；放弃的 URL 写进日志或失败清单，供人工复查。

## 8.6 logging：让脚本可审计

print 的问题：没有时间戳、没有级别、没法按需开关、输出和业务数据混在一起。标准 logging 配置模板（本仓库各 lab 的直接可用版）：

```python
import logging

def setup_logging(log_file: str = "data/crawler.log") -> logging.Logger:
    logger = logging.getLogger("crawler")        # 命名 logger,避免污染 root
    logger.setLevel(logging.INFO)
    fmt = logging.Formatter(
        "%(asctime)s %(levelname)s [%(name)s] %(message)s", "%Y-%m-%d %H:%M:%S"
    )
    sh = logging.StreamHandler()                 # 控制台:看实时进度
    sh.setFormatter(fmt)
    fh = logging.FileHandler(log_file, encoding="utf-8")  # 文件:事后审计
    fh.setFormatter(fmt)
    logger.addHandler(sh)
    logger.addHandler(fh)
    return logger

logger = setup_logging()
logger.info("开始采集: %s", BASE_URL)       # 用 %s 惰性格式化,不用 f-string
logger.warning("第 %d 页重试 %d 次", page, attempt)
logger.error("放弃 URL: %s", url)
```

日志文件输出示例：

```text
2026-11-04 01:10:22 INFO [crawler] 开始采集: https://quotes.toscrape.com
2026-11-04 01:10:24 INFO [crawler] 第 3 页完成, 10 条
2026-11-04 01:10:26 WARNING [crawler] 第 5 页重试 1 次
```

三件事按第 6 章合规清单落到日志：**采集了什么目标、什么时间、多少量**——出问题时这就是你的辩护材料与排查线索。级别约定：INFO 记进度（每页一条，不是每条数据一条）、WARNING 记可自动恢复的异常（重试）、ERROR 记放弃的事件。

## 8.7 监控思路与调度

### 8.7.1 监控的最小闭环

工程级爬虫每天定时跑，没人盯着，监控回答两个问题：**跑没跑成**、**数据对不对**。最小闭环四件套：

1. **退出码**：成功 0、失败非 0——所有调度器都认它；
2. **心跳日志**：任务开始/结束/条数写日志（8.6），日志本身可被收集告警（Ubuntu 篇第 10 章的运维体系）；
3. **数据量断言**：任务末尾校验 `新增条数 < 预期下限则报警`——爬虫最隐蔽的失败是「成功跑完但采到 0 条」（站点改版，第 3 章的坑在这里兑现）；
4. **产物时间戳**：`data/` 里最新文件时间就是最近一次成功运行的时间，一行 `ls -lt` 即体检。

### 8.7.2 调度：APScheduler 与 cron

| 维度 | cron（系统级） | APScheduler（Python 库） |
|---|---|---|
| 形态 | 系统守护进程，crontab 表达式 | 进程内调度器，Python 代码配置 |
| 精度 | 分钟 | 秒 |
| 依赖 | 系统自带（Ubuntu 篇已学） | `pip install apscheduler` |
| 适用 | 固定时刻跑脚本（服务器标准姿势） | 程序内部的多任务编排、错过补跑、动态增删任务 |

cron 方式（服务器主线，详见 Ubuntu 篇）：

```bash
crontab -e
# 每天 02:30 跑采集(注意写 venv 内 python 绝对路径,cron 的 PATH 是精简的)
30 2 * * * /home/<your-username>/opt/jjyv/bin/python /path/to/crawler.py >> /path/to/data/cron.log 2>&1
```

APScheduler 方式（程序内）：

```python
from apscheduler.schedulers.blocking import BlockingScheduler

sched = BlockingScheduler()
sched.add_job(run_crawler, "cron", hour=2, minute=30)   # 与 cron 表达式同语义
sched.start()   # 阻塞运行,适合「调度器即主程序」的容器部署
```

选择：**部署在 Ubuntu 服务器上、每天定时跑一次 → cron**；应用进程内多个采集/分析任务协同 → APScheduler。两者不冲突，cron 也可以只负责启动一个「内含 APScheduler 的常驻进程」。

## 8.8 配置化与 .env：密钥不进代码

把「会变的东西」从代码里拿出来：目标 URL、延迟、并发数、数据库密码。Python 标准做法是 `.env` 文件 + `os.environ`：

```bash
# projects/crawler-lab/.env （此文件不进 git！）
CRAWLER_BASE_URL=https://quotes.toscrape.com
CRAWLER_DELAY=0.3
CRAWLER_CONCURRENCY=5
MYSQL_PASSWORD=<your-password>       # 密钥只放这里
```

```python
import os
from dotenv import load_dotenv        # pip install python-dotenv

load_dotenv()
BASE_URL = os.environ.get("CRAWLER_BASE_URL", "https://quotes.toscrape.com")
DELAY = float(os.environ.get("CRAWLER_DELAY", "0.3"))
```

安全要点（呼应 STYLE_GUIDE 密钥红线）：`.env` 写进 `.gitignore`（本仓库根 `.gitignore` 已配置）；仓库里放 `.env.example`（只含键名不含值）告诉协作者需要哪些配置；MySQL 密码等密钥**只存在于 .env 或系统环境变量**，代码里永远不出现字面量。

## 常见坑与排查（Troubleshooting）

| 现象 | 原因 | 解决办法 |
|---|---|---|
| `RuntimeError: no running event loop` / 协程没执行 | 忘了 `asyncio.run(main())`，或调用了协程函数没 await | 入口必须 `asyncio.run()`；协程内的调用要 `await`，直接调用只会得到协程对象 |
| 异步比同步还慢 | 协程里混入 CPU 密集代码或同步 requests，阻塞事件循环 | 协程只做 IO；HTTP 用 httpx.AsyncClient；CPU 活放进程池 |
| `TimeoutError` 零星出现且集中在高峰期 | 并发数对目标站过大，触发限流 | 调小 Semaphore 与每请求延迟；重试退避拉长（不是调大并发） |
| 重跑采集数据重复/翻倍 | 没有断点状态，或状态文件没和去重约束配合 | 8.5.1 的 seen 集合 + 第 4 章数据库唯一键双层兜底 |
| 任务「成功」但数据是 0 条 | 站点改版，选择器全失效 | 8.7.1 的数据量断言报警；日志里加「解析命中数」指标 |
| 日志文件全是重复行 | 多次 addHandler（模块被重复导入/多次 setup） | 用命名 logger + 配置只做一次；或 `logger.handlers.clear()` 再加 |
| cron 任务没跑/报 ModuleNotFoundError | cron 的 PATH 与环境不同（没激活 venv） | crontab 里写 venv python 绝对路径；`sys.path`/工作目录在脚本内处理 |
| `.env` 里的值读不到 | 文件位置不对（load_dotenv 默认从当前目录找） | `load_dotenv(Path(__file__).parent / ".env")` 按脚本位置定位 |
| 断点续爬后跳过了部分页面 | 状态文件在抓取中途损坏（写一半被杀） | 写临时文件再原子替换（`Path.replace`）；或改用 SQLite 存状态 |
| `gather` 一个任务失败全部取消 | 忘了 `return_exceptions=True` | 批量采集显式开启，异常当结果结算（8.3.1） |
