## 6.6.1 开发 vs 生产：差距清单

| 维度 | 开发环境 | 生产环境 |
|---|---|---|
| 服务器 | `uvicorn --reload` 单进程 | 多 worker、无 reload、进程守护 |
| 配置 | .env 随手改 | 环境变量注入 + 密钥管理 |
| 文档 | /docs 开放 | 关闭或加访问控制 |
| 数据库 | SQLite 随意重建 | MySQL/PostgreSQL + 备份 |
| 日志 | 控制台 | 结构化日志 + 轮转 + 告警 |
| 错误 | 堆栈直出 | 隐藏堆栈，保留 trace id |

`06_deploy/main.py` 的 `Settings` 类把这些变成**可执行的检查**：

```python
def unsafe_for_production(self) -> list[str]:
    problems = []
    if self.app_env == "production":
        if not self.secret_key:
            problems.append("SECRET_KEY 未设置")
        if self.debug:
            problems.append("APP_DEBUG 在生产必须为 false")
        if self.database_url.startswith("sqlite"):
            problems.append("生产建议 MySQL/PostgreSQL")
    return problems

@app.get("/healthz")
def healthz() -> dict:
    problems = settings.unsafe_for_production()
    return {"status": "degraded" if problems else "ok", "app_env": settings.app_env, "problems": problems}
```

实测输出：

```text
$ curl -s http://127.0.0.1:8106/healthz
{"status":"ok","app_env":"dev","python":"3.14.0","problems":[]}

$ curl -s http://127.0.0.1:8106/config
{"app_env":"dev","debug":false,"database_url":"sqlite:///./data/lab06.db",
 "log_level":"INFO","secret_key_set":false}
```

注意 `config` 端点只报告 `secret_key_set: false`（是否设置），**绝不回显值**——这也是一个安全细节。

## 6.6.2 配置分层（12-factor）

```text
代码仓库里：.env.example   ← 键名清单 + 说明，唯一入库的配置文件
本地机器上：.env           ← 真实值，.gitignore 覆盖，绝不提交
CI/服务器：环境变量        ← GitHub Secrets / systemd Environment / export
```

读取优先级：环境变量 > .env > 默认值。`load_dotenv()` 只做「把 .env 注入环境变量」这一件事。

## 6.6.3 进程模型：worker 与守护

```bash
# 开发
uvicorn main:app --reload

# 生产（单机多 worker；CPU 密集型 worker 数 ≈ 核数）
uvicorn main:app --host 127.0.0.1 --port 8000 --workers 2
```

- 绑定 127.0.0.1：公网流量由 Nginx 进来，uvicorn 不直接暴露
- worker 是独立进程，GIL 之外再吃满多核
- 进程崩溃自愈交给 systemd（`Restart=on-failure`），开机自启交给 `enable`

systemd 单元文件与逐行讲解：[Ubuntu·systemd 篇](../02-linux-ubuntu/04-软件包管理apt与系统服务systemd.md)；完整部署时间线：[第 07 章·部署上线](../07-final-project/05-测试CI与部署上线.md)。

## 6.6.4 Nginx 反向代理（为什么与怎么做）

| Nginx 的职责 | 说明 |
|---|---|
| TLS 终结 | certbot 一键 HTTPS，Python 进程只管 HTTP |
| 静态文件 | 前端/图片直接由 Nginx 吐出，不占 Python worker |
| 缓冲与超时 | 慢客户端不占用应用 worker |
| 多站点 | 一台机器多个域名各指各的上游 |

```nginx
server {
    listen 443 ssl;
    server_name your.domain.com;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`X-Forwarded-*` 三件套的作用：FastAPI 在uvicorn 后面拿到的「客户端 IP」是 Nginx 的——把这些头传过去，应用才能还原真实来源（限流/审计都靠它）。

## 6.6.5 日志、健康检查与监控

- **日志**：uvicorn 访问日志 + 应用日志（logging 模板见 [爬虫工程化](../03-python-crawler/08-爬虫工程化(并发-调度-监控).md)）；journalctl -u <service> -f 实时跟踪；logrotate 管轮转
- **healthz**：进程活着 ≠ 服务可用——healthz 里顺带探测数据库（连接失败返回 degraded，监控据此告警）
- **监控**：uptime-kuma 等拨测 healthz；错误率/延迟从 Nginx 日志统计

## 6.6.6 Docker（概念 + 最小文件）

本机无 Docker 环境时，先理解两个概念：**镜像**（打包了代码+依赖的只读模板）、**容器**（镜像的运行实例）。最小 Dockerfile：

```dockerfile
FROM python:3.14-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]
```

在装有 Docker 的服务器上：`docker build -t book-insight . && docker run -p 8000:8000 book-insight`。与 systemd 方案二选一即可；容器化的真正收益在「环境一致性 + 编排扩展」（Compose/K8s），教学项目 systemd 足够。

## 常见坑与排查

| 现象 | 原因 | 解决 |
|---|---|---|
| 生产 502 | worker 挂了/端口不对 | systemctl status + journalctl 定位 |
| --workers 后内存翻倍 | 每个 worker 独立进程 | 调 worker 数；连接池按 worker 配 |
| .env 改了没生效 | 未重启进程 | systemd 下 `restart`；或用 --env-file |
| 504 超时 | 慢接口超过 Nginx 默认 60s | 优化查询或调 proxy_read_timeout |
| HTTPS 后 cookie 异常 | secure/samesite 属性 | 按规范设置（本教程用 Bearer 不受影响） |
| 容器内连不上宿主库 | 网络隔离 | host.docker.internal 或 compose 网络 |
