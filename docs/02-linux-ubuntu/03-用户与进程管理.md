# 第 3 章 · 用户与进程管理

> 本章配套代码：无固定仓库代码，练习在服务器终端完成；进程与端口实验用的临时文件放 `/tmp/proc-lab/`。
> 建议学习时长：约 3 小时

## 学习目标

学完本章，你能够：

1. 说清 `adduser` 与 `useradd` 的区别，会创建服务专用用户、把用户加入 sudo 组；
2. 读懂 `/etc/passwd` 与 `/etc/shadow` 每个字段的含义，解释 visudo 为什么不能直接用编辑器改；
3. 用 `ps aux`、`top`/`htop` 定位进程，理解 kill 信号机制，说明 `nohup + &` 方案在服务器上的局限；
4. 用 `jobs/fg/bg/Ctrl-Z` 在前后台之间调度任务；
5. 用 `free -h`、`df -h`、`du -sh *`、`uptime`、`lsof -i:8000` 完成一次「服务器体检」，并定位端口占用。

## 3.1 前置知识 / 本章地位

第 2 章你学会了「操作文件」，本章解决「谁在操作」和「谁在运行」两个问题：**用户与权限是安全的地基，进程与资源是运维的日常**。

部署 FastAPI 项目后的典型场景会反复用到本章：爬虫挂在后台跑、服务卡死要 kill、端口被占要找出元凶、内存爆了要判断 OOM。第 4 章的 systemd 会给出比 `nohup` 正确得多的服务管理方案，但只有理解了「为什么 nohup 不够」，你才能真正理解 systemd 解决了什么。

## 3.2 用户与组管理

Linux 是多用户系统：每个进程都以某个用户身份运行，每个文件都归属于某个用户和组。**「服务专用用户」是服务器安全的核心习惯**——FastAPI 应用不需要是你的登录用户，更不应该是 root。

### 3.2.1 adduser 与 useradd 的区别

两个命令极易混淆：

- **`adduser`**：友好的交互式高层封装（Debian/Ubuntu 系特有），自动创建家目录、复制骨架文件（`.bashrc` 等）、设置密码、询问信息。**日常用它**。
- **`useradd`**：底层通用命令，所有 Linux 发行版都有，默认行为很「生」——不建家目录、不设密码，必须配合 `-m`（创建家目录）、`-s`（指定 shell）等参数，最后还要单独 `passwd`。**脚本和精确控制用它**。

```bash
# 方式一：adduser（推荐手动场景）
sudo adduser deploy
# 交互：设置密码、FullName 等信息（其余可直接回车跳过）

# 方式二：useradd 一条龙（适合写进部署脚本）
sudo useradd -m -s /bin/bash -c "book-insight service" svcapp
sudo passwd svcapp    # 单独设置密码
```

**服务专用用户**的进阶写法——系统用户（system account），不能登录、没有密码，纯粹给进程用：

```bash
sudo adduser --system --group --home /opt/book-insight --shell /usr/sbin/nologin booksvc
```

`--shell /usr/sbin/nologin` 让这个用户无法登录 shell（但进程可以以它身份运行），攻击者即使拿到这个「账号」也没有入口。systemd 服务文件里 `User=booksvc`（第 4 章）就是用它。

### 3.2.2 passwd 与 usermod

```bash
sudo passwd deploy            # 给用户改/设密码（root 执行不需要旧密码）
passwd                        # 改自己的密码
sudo usermod -aG sudo deploy  # 把 deploy 加入 sudo 组（获得管理员权限）
id deploy                     # 查看用户的 uid、gid 和所属组
whoami                        # 我当前是谁
groups                        # 我在哪些组里
```

`usermod -aG` 的 `-a`（append）**绝对不能漏**：`usermod -G sudo deploy`（没有 -a）会把用户的其他附加组全部抹掉只剩 sudo——经典事故。`-G` 后多个组用逗号分隔：`-aG sudo,docker deploy`。

改完组要**重新登录**才生效（组的身份在登录会话建立时确定）。验证：`id` 输出里应出现 `sudo`。

### 3.2.3 /etc/passwd 与 /etc/shadow 字段解读

用户信息存放在两个文件里，读懂它们就能看懂系统的用户世界：

```bash
cat /etc/passwd
```

预期输出（节选）：

```text
root:x:0:0:root:/root:/bin/bash
ubuntu:x:1000:1000:Ubuntu,,,:/home/ubuntu:/bin/bash
booksvc:x:998:998::/opt/book-insight:/usr/sbin/nologin
```

每行 7 个字段（冒号分隔）：

| 字段 | 示例 | 含义 |
|---|---|---|
| 1 用户名 | `ubuntu` | 登录名 |
| 2 密码位 | `x` | `x` 表示真密码在 shadow 里（历史兼容） |
| 3 UID | `1000` | 用户 ID，0 是 root；1-999 通常是系统用户；普通用户从 1000 起 |
| 4 GID | `1000` | 主组 ID |
| 5 GECOS | `Ubuntu,,,` | 备注/全名 |
| 6 家目录 | `/home/ubuntu` | 登录后所在目录 |
| 7 shell | `/bin/bash` | 登录 shell；`/usr/sbin/nologin` 表示不可交互登录 |

```bash
sudo cat /etc/shadow
```

预期输出（节选，密码字段是哈希值）：

```text
ubuntu:$y$j9T$xxxxxxxxxxxxxxxxxxxxxxxxxxxx/:20345:0:99999:7:::
booksvc:!:20345:0:99999:7:::
```

9 个字段里最值得认识的：字段 2 是密码哈希（`$y$` 开头是 yescrypt 算法；`!` 或 `*` 表示没有可用的密码，即不能密码登录——服务用户就该这样）；字段 3-5 是密码修改间隔策略。普通用户**读不了** shadow（`000` 权限，root 专属），这正是密码哈希与 passwd 文件分离的原因——passwd 需要全局可读，而哈希必须锁起来。

### 3.2.4 sudoers 与 sudo 组、visudo

sudo 的授权规则在 `/etc/sudoers`，以及更现代的 `/etc/sudoers.d/` 目录（Ubuntu 24.04 已默认把 `%sudo ALL=(ALL:ALL) ALL` 规则写在 `/etc/sudoers` 主文件里）。

**为什么必须用 `visudo` 而不能直接 `vim /etc/sudoers`？** visudo 做了三件编辑器做不到的事：①保存前做**语法校验**，写错了不允许保存；②防止两个管理员同时编辑互相覆盖；③（部分版本）带锁。sudoers 语法错误是灾难级的——一旦解析失败，**所有人（包括 root 之外的你）都无法 sudo**，等于把自己锁在管理员权限之外，只能靠云控制台 VNC 救援。

推荐做法：不在主文件里改，往 `/etc/sudoers.d/` 放独立规则文件：

```bash
sudo visudo -f /etc/sudoers.d/deploy    # 用 visudo 打开（它就是编辑器包装器）
```

写入一条经典规则——允许 deploy 用户免密重启应用服务：

```text
deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart book-insight, /usr/bin/systemctl status book-insight
```

格式为「用户 主机=(以谁的身份) 命令列表」。这比「免密一切命令」（`NOPASSWD: ALL`）安全得多：自动化脚本（第 6 章部署脚本）能重启服务，但拿不到完整 root。语法参考以 `man sudoers` 为准。

## 3.3 进程查看与控制

### 3.3.1 进程是什么

运行的程序实例就是进程（process），每个进程有唯一 PID。进程之间是树：你 SSH 进来那个 bash 是 sshd 的子进程，在 bash 里启动的 python 是 bash 的子进程。父进程退出通常会把子进程托付给 init（PID 1，systemd）。

### 3.3.2 ps aux

```bash
ps aux
```

预期输出（节选）：

```text
USER   PID %CPU %MEM    VSZ   RSS TTY  STAT START  TIME COMMAND
root     1  0.0  0.4 167016  8960 ?    Ss   09:00  0:02 /sbin/init
ubuntu 1234  0.2  1.1  45220 23000 pts/0 Ss  10:01  0:00 -bash
ubuntu 1301  1.8  3.2 180220 66000 pts/0 S+  10:05  0:03 python3 -m http.server 8000
```

逐列解读：`USER` 属主；`PID` 进程号（kill 用它）；`%CPU/%MEM` 占用比；`RSS` 常驻内存（KB）；`STAT` 状态码——`R` 运行、`S` 可中断睡眠、`D` 不可中断 IO 等待、`Z` 僵尸（父进程没回收）、`T` 暂停，附加标记 `s` 会话首进程、`+` 前台；`COMMAND` 启动命令。

常用过滤姿势：

```bash
ps aux | grep uvicorn          # 找 uvicorn 进程
ps aux --sort=-%mem | head     # 按内存倒序（top 5 内存的进程）
ps -ef --forest                # 树状显示父子关系
```

`ps aux | grep xxx` 会多出一条 grep 自身，可用 `grep [u]vicorn` 技巧或 `pgrep -af uvicorn`（更干净）。

### 3.3.3 top 与 htop

```bash
top        # 自带；按 P 按CPU排序、M 按内存、q 退出
sudo apt install htop -y
htop       # 彩色交互版，F9 送信号、F6 改排序、F10 退出
```

top 头部五行的含义必须会读（服务器体检的核心指标）：`load average: 0.52, 0.58, 0.59` 是 1/5/15 分钟平均负载（经验法则：持续超过 CPU 核数就是过载，核数看 `nproc`）；`%Cpu(s)` 里 `us` 用户态、`sy` 内核态、`wa` 等磁盘 IO（wa 高说明瓶颈在磁盘）；`MiB mem` 一行注意 `avail` 才是真正可用内存（Linux 会把空闲内存拿去当缓存 buff/cache，所以 used 大不代表紧张）。

### 3.3.4 kill 与信号

kill 名字有误导性——它「发送信号」，终止只是其中一种信号的效果：

```bash
kill 1301            # 默认 SIGTERM(15)：请求进程自己清理退出（优雅终止）
kill -9 1301         # SIGKILL(9)：内核直接掐死，进程没有任何清理机会
kill -HUP 1301       # SIGHUP(1)：许多守护进程约定「重读配置文件」
kill -l              # 列出全部信号
pkill -f "python3 -m http.server"   # 按命令行模式发信号（注意别误伤）
```

纪律：**先 `kill`（TERM）给进程收尾机会——落盘、关连接、写退出日志；几秒后还活着再 `kill -9`**。数据库进程（如 MySQL）被 -9 的后果是恢复时间变长甚至数据风险，切记 TERM 优先。为什么 -9 无法被进程拦截？因为 SIGKILL 由内核直接执行，不经过进程的信号处理函数——这是它「必死」的原因，也是它「危险」的原因。

### 3.3.5 nohup 与 & 的局限

在没有 systemd 服务化之前，让命令在断开 SSH 后继续活着的传统做法：

```bash
nohup python3 crawl_books.py > crawl.log 2>&1 &
```

`&` 把任务丢到后台；`nohup` 让进程忽略 SIGHUP——因为**SSH 会话退出时，系统会给该会话的进程发 SIGHUP**，普通进程收到就退了。

这套方案能用，但有四个它解决不了的坑：

1. **进程死了没人拉起来**：爬虫半夜崩了，明早才发现日志停在凌晨 3 点；
2. **不随开机自启**：服务器重启后要人肉重新挂；
3. **stdout/stderr 靠自己重定向**，日志没有轮转、没有时间戳结构；
4. **找不到「服务」的概念**：`systemctl restart` 之类的标准运维动作不存在，全靠记住 PID 或 pgrep。

对照组：同样的事交给 systemd（第 4 章），崩溃自动重启、开机自启、journald 统一日志一条龙。**结论：临时挂个一次性任务用 nohup 可以，任何「长期运行的服务」一律写 systemd unit。**

## 3.4 前台后台任务：jobs / fg / bg / Ctrl-Z

shell 内置的任务控制，适合交互场景的临时调度：

```bash
python3 -m http.server 8000     # 前台运行，占用终端
# 按 Ctrl-Z                     # 暂停（STAT 变 T），shell 提示 [1]+ Stopped
jobs                            # 查看本 shell 的任务列表
bg %1                           # 让 1 号任务在后台继续跑
fg %1                           # 拉回前台
python3 -m http.server 8000 &   # 直接后台启动，输出仍混在当前终端
disown %1                       # 从 shell 任务表移除（exit 后不再收到 SIGHUP）
```

`jobs` 预期输出：

```text
[1]+  Running                 python3 -m http.server 8000 &
```

和 `nohup &` 的关系：`Ctrl-Z` + `bg` 等价于「先跑了发现是长任务，转后台」，比 kill 掉重来优雅。这套机制只在**同一个 shell 会话**内有意义，SSH 断开还是靠 nohup/disown/systemd。

## 3.5 系统资源速查：free / df / du / uptime / lsof

这五个命令构成一次完整的「服务器体检」，先看谁、看什么：

```bash
uptime           # 负载与运行时长（top 的浓缩版）
free -h          # 内存（-h 人类可读）
df -h            # 各文件系统磁盘使用率
du -sh *         # 当前目录下各项体积（-s 汇总）
sudo lsof -i:8000   # 谁占着 8000 端口
```

`free -h` 预期输出：

```text
               total        used        free      shared  buff/cache   available
Mem:           3.8Gi       1.2Gi       1.5Gi        12Mi       1.1Gi       2.4Gi
Swap:             0B          0B          0B
```

解读要点：**看 `available` 列判断内存够不够**，不要看 free（Linux 积极用空闲内存做缓存是特性不是故障）；Swap 为 0 的 1-2G 小内存服务器建议按第 10 章清单加 swap，防止 MySQL/OOM 一击致命。

`df -h` 预期输出（节选）：

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        40G   6.2G   32G  17% /
tmpfs           2.0G     0  2.0G   0% /dev/shm
```

`Use%` 超过 80% 就该警惕（第 10 章有「磁盘满」故障演练）。定位大文件用 `sudo du -sh /var/* | sort -rh | head` 逐层下钻。

**端口占用排查**（部署时最高频问题之一：`Address already in use`）：

```bash
sudo lsof -i:8000
```

预期输出：

```text
COMMAND   PID   USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
python3  1301 ubuntu    3u  IPv4  29345      0t0  TCP *:8000 (LISTEN)
```

拿到 PID 后 `kill <pid>` 即可。等价工具 `ss -tlnp`（第 5 章详解，`-p` 显示进程）：

```bash
sudo ss -tlnp | grep 8000
```

## 常见坑与排查（Troubleshooting）

| 报错/现象 | 原因 | 解决办法 |
|---|---|---|
| `usermod -G sudo xxx` 后用户丢失 docker 等组 | 漏了 `-a` | 补加回来；养成肌肉记忆 `-aG` |
| 加组后权限没生效 | 组身份在登录时确定 | 重新登录（exit 后重连）或 `newgrp <组名>` |
| 误改 sudoers 导致 sudo 全挂 | 直接编辑未校验 | 云控制台 VNC 登录救援；今后只用 visudo/sudoers.d |
| `kill -9` 后进程还在 | 它处于不可中断 IO 等待（STAT D），或成了僵尸 | 等待 IO 完成；僵尸等父进程回收，实在不行重启 |
| nohup 的任务 SSH 退出后还是没了 | 管道另一端进程（如 `| tee`）没被 nohup 覆盖 | 整条命令都放进 nohup bash -c '...'，或改用 systemd |
| `Address already in use` 启动失败 | 端口被旧进程占着 | `sudo lsof -i:8000` 找 PID kill；或 `pkill -f 旧命令` |
| 内存看 used 很高吓一跳 | buff/cache 占用是正常机制 | 看 `available` 列 |
| 负载高但 CPU 不高 | 瓶颈在磁盘 IO（wa 高）或大量不可中断进程 | top 看 `%wa`，`iostat -x 1`（sysstat 包）跟进 |

## 动手练习

1. **建服务用户并体验最小权限**：创建 `--shell /usr/sbin/nologin` 的系统用户 `booksvc`，用它归属一个 `/opt/proc-lab` 目录，然后验证你无法 `sudo -u booksvc bash` 获得交互 shell（会被 nologin 拒绝），但 `sudo -u booksvc ls /opt/proc-lab` 可以。
   <details><summary>提示</summary>这就是服务用户的形态：进程可以它身份运行，人却登不进去。第 4 章 systemd 的 User= 将直接使用它。</details>
2. **写一条 NOPASSWD 精确规则**：用 `visudo -f /etc/sudoers.d/proc-lab` 允许你的用户免密执行 `systemctl restart <自建服务名>`，验证生效且其他 sudo 命令仍要密码。
   <details><summary>提示</summary>规则里命令要写绝对路径（`which systemctl` 确认）。测试：`sudo -n systemctl status ssh` 应要求密码，你的白名单命令应免密。</details>
3. **进程侦查**：启动两个 `python3 -m http.server`（端口 8000、8001），用 `ps aux`、`pgrep -af`、`sudo lsof -i:8000` 三种方式找到它们；先用 TERM 结束 8000 那个，观察它退出；对 8001 先发 `kill -STOP` 再用 `ps` 看 STAT 变 `T`，最后 `kill -CONT` 恢复。
   <details><summary>提示</summary>`kill -STOP <pid>` 与 Ctrl-Z 同效但可远程操作；`kill -CONT <pid>` 恢复运行。信号语义表见 `kill -l`。</details>
4. **一次完整体检**：依次跑 `uptime`、`free -h`、`df -h`、`du -sh /var/log`、`sudo ss -tlnp`，把结果记进笔记，判断这台服务器当前健康状态与风险点。
   <details><summary>提示</summary>关注三点：负载是否低于核数、available 是否充足、根分区 Use% 是否低于 80%。这是第 10 章上线检查的单机版。</details>
